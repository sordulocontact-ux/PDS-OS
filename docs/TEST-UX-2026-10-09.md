# Test UX — parcours complet, du nouvel artiste à la sortie (09/10/2026)

## Méthode

- **Test réel dans Chrome** sur `pnpm dev`, en jouant les rôles comme au quotidien :
  - le DG (`admin@pds.test`) : créer l'artiste, deux titres et le projet EP, puis le transmettre ;
  - la cheffe de projet (`cp-conception@pds.test`) : accepter le projet, faire le Cadrage guidé et créer le Brief.
  - Projet de test : **« Nuit claire (EP) »**, artiste **Selma Orane**, titres « Nuit claire » et « Ciel bas » (avec un sample de piano), sortie le 4/12, budget de 8 000 €.
- **Revue cognitive d'après le code** pour la suite du parcours :
  - méthode : à chaque étape, l'utilisateur sait-il quoi faire, voit-il le contrôle, comprend-il le contrôle, comprend-il le retour ? ;
  - étapes couvertes : Plan du projet, Master, Juridique, Marketing, Distribution, Pilotage ;
  - raison : le test réel n'a pas pu aller plus loin (voir « Limites »).
- **Sévérité** selon l'échelle de Nielsen :
  - 4 = bloque le travail ;
  - 3 = majeur ;
  - 2 = mineur ;
  - 1 = cosmétique.
- **Provenance de chaque constat** :
  - **[Testé]** : vécu dans le navigateur ;
  - **[Code]** : déduit du code, avec le fichier en preuve ;
  - **[Vérifié]** : constat d'agent relu dans le code.

## Limites du test

- **Machine saturée.** Pendant le test, une autre session lançait 3 navigateurs Playwright (comptes UX-A à UX-D), puis une 2ᵉ pile Supabase (`sordulo-os`) a démarré. La charge système est montée de 35 à 190, et le pool de connexions a saturé. **La lenteur mesurée n'est donc pas imputable à l'app.** Seule compte ici la façon dont l'app réagit aux pannes.
- **Validation du Brief forcée en base.** L'autre session avait créé un 2ᵉ DG, ce qui bloquait la validation. Avec l'accord de Sacha, la demande de validation du Brief a été écrite directement en base. Le projet « Nuit claire (EP) » attend maintenant la validation du DG.

- Les erreurs s'affichent en rouge au bon endroit.

## Ce qui manque pour un usage quotidien

1. **Prévenir les personnes** : e-mails au mixeur, aux personnes extérieures et au DG (modèle à valider), relances, rappels d'échéance.
2. **Écouter dans l'app** : la source, les versions V1/V2 en A/B, le master final.
3. **Livrer réellement la sortie** : checklist distributeur (fichiers, artwork, métadonnées, crédits, ISRC par titre, UPC), date de livraison.
4. **Une seule saisie par fait** : date de sortie, enveloppe, personnes (Réseau partout), éditeur, parts.
5. **Corriger ses erreurs** : modifier ou supprimer une tâche, annuler une validation de mix, rouvrir une Stratégie, changer l'échéance ou l'enveloppe.
6. **Une seule carte du projet** : workflows *ou* 7 étapes, pas les deux. Des étapes qui mènent jusqu'au bilan.
7. **Une vue calendrier et une recherche globale.**

## Ce qui est déjà fort

- Le Cadrage guidé : une question à la fois, chaque proposition sourcée et citée, rien d'écrit sans clic humain.
- Les explications honnêtes : chaque action dit pourquoi, et l'écran dit ce qui n'est pas intégré.
- Les formulaires repris d'une page à l'autre, les validations en rouge au bon endroit, le brouillon automatique du projet.
- Les statuts calculés par le code, avec leur raison.
